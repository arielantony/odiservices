# Project Constitution — OdiServices

Principles that govern the development of the OdiServices Portal. They apply to
anyone, human or AI agent, who contributes to the project.

## Article 1 — Language

**English is the primary language of the project.** It is used for:

- documentation and project content (`docs/`, READMEs, specs, backlog);
- file and folder names;
- code, identifiers and comments;
- commit messages, pull requests and issues.

The exception is the text that end users read in the interface (labels,
buttons, messages). The portal's users are Brazilian, so that text stays in
Brazilian Portuguese, both in the prototypes and in `app/`.

## Article 2 — Frontend: HTML prototype before code

Every requested frontend change **must first be prototyped in a static HTML
file**. This covers new screens, layout changes, components, flows, styles,
interface copy and visual behavior. The prototype is presented for review and
only then implemented in `app/`.

The required flow is:

1. **Prototype**: design the change in a self-contained HTML file under
   `docs/prototypes/` (see Article 3).
2. **Verify**: the author opens the file in a browser and fixes anything broken
   before presenting it (see Article 4).
3. **Present**: deliver the prototype to the team with a summary of the design
   decisions (see Article 5).
4. **Review**: the team reviews it. Each round of changes produces a new
   prototype version until it is approved.
5. **Implement**: only after approval is the change implemented in `app/`, and
   it must match the approved version exactly.

The step-by-step process, from the product owner's brief and the clarifying
questions to stories and implementation, is described in
`docs/FRONTEND_GUIDELINES.md`.

Additional rules:

- No frontend change is implemented without an approved prototype.
- If the approved design needs to change during implementation, the change goes
  back to the prototype for a new review before the code continues.
- The approved prototype is the source of truth for the design. The code must
  reflect it.

## Article 3 — How the prototype is built

- **One file per version.** It must open with a double click, with no server
  and no build step. CSS is inline, and images such as the logo are embedded as
  base64. The only external dependency allowed is Google Fonts.
- **One section per screen.** Each screen is a `.screen` element with a fixed
  desktop width of 1360 px. Screens are stacked vertically, and each is titled
  with its version and name, for example `v3 · Categorizer — Board`.
- **Odisseia visual identity.** Colors, typography, logo and motifs follow
  `docs/BrandGuidelines.pdf`, whose pages are available as JPG in
  `docs/BrandGuidelines/`. Color tokens are declared in `:root` at the top of
  the file. Any deviation from the guidelines must be recorded in the
  presentation summary. Reasons for a deviation include an unavailable font,
  insufficient contrast or poor legibility.
- **Minimum accessibility.** Small text needs AA contrast (4.5:1).
  Low-contrast colors are limited to large titles, rules and decorative
  elements. An example is orange `#EE5E27` on a light background.
- **Fictitious data only.** Prototypes never contain real customer, supplier or
  financial transaction data (see the security notes in `docs/BACKLOG.md`).
- **Versions are never overwritten.** Each review round produces a new file
  (`v1.html`, `v2.html`, `v3.html`…) in `docs/prototypes/<feature>/`, so the
  history of what was discussed is preserved.
- If the HTML is generated by a script (template + data), the script and
  template live in the same folder as the version, so it can be regenerated.

## Article 4 — Verification before presenting

Before presenting, the prototype is opened in a browser and checked against a
full-page screenshot. A person can do this, or an agent can do it via the
Chrome DevTools MCP. At minimum, check that:

- no text overflows, gets clipped or wraps where it shouldn't;
- no elements overlap;
- fonts load correctly, with no fallback to a system font;
- colors and surfaces match the declared tokens.

A prototype with a known visual defect is not presented unless the defect has
been fixed or is explicitly called out.

**Release the browser when done.** The Chrome DevTools MCP keeps one Chrome
instance on a shared profile (`~/.cache/chrome-devtools-mcp/chrome-profile`).
If it stays open, the next agent fails with "The browser is already running".
Whoever opens it closes it as soon as the check is finished:

1. Close every page opened for the check (`close_page`). The last page cannot
   be closed through the tool.
2. Quit the Chrome instance that holds the profile:
   `pkill -f "chrome-devtools-mcp/chrome-profile"`. The pattern matches only
   that profile, so a person's own Chrome is not touched.
3. Stop the dev or preview server started for the check.
4. If a later launch still reports a running browser, remove the stale locks:
   `rm ~/.cache/chrome-devtools-mcp/chrome-profile/Singleton*`.

Never kill a browser that was already open before the check started, and
never leave the profile locked at the end of a session.

## Article 5 — Presentation

The review delivery contains:

1. the path to the version's HTML file;
2. what changed compared with the previous version, or with the current screen
   in `app/`;
3. how the brand guidelines were applied, and where they were not followed and
   why;
4. open questions that need a decision from the team.

## Article 6 — Pull requests

**Every implementation of a story or task results in a pull request on
GitHub,** opened with the GitHub CLI (`gh pr create`). Nothing is implemented
directly on `main`.

- **One unit of work per PR.** A PR implements one backlog item, or one step
  of an item. It never mixes unrelated items.
- **Small and concise.** A PR changes fewer than 500 lines, so it can be
  reviewed properly. Lockfiles (`yarn.lock`, compiled `requirements*.txt`)
  and binary assets don't count toward the limit.
- **Complex work is split.** An item that would exceed the limit is broken
  into smaller steps, each delivered in its own PR. The steps are listed in
  the item's spec, and each step leaves the app working and its tests
  passing.
- **Each backlog item gets a feature branch from `main`.** An item split
  into steps gets a feature branch, `feature/<id>-<slug>` (for example
  `feature/fe-23-react-app`). It is created from the latest `origin/main`
  and pushed before the first step starts. Nobody commits to it directly: it
  changes only through merged step PRs and through merges of `main`.
- **Each step is a branch from the feature branch, merged back by a PR.** A
  step branch, `<type>/<id>-step-<n>-<slug>` (for example
  `feat/fe-23-step-2-api-client`), starts from the latest feature branch,
  and its PR targets the feature branch. The owner reviews and merges each
  step PR. The next step starts from the feature branch after the previous
  step has been merged into it, so steps never stack on each other's
  branches.
- **The feature branch reaches `main` only when the item is complete.**
  When every step is merged and the spec's verification is done, a final PR
  from the feature branch to `main` closes the item.
  - Its description lists the step PRs and repeats the How to test and
    Verification sections for the whole item.
  - The 500-line limit applies to the step PRs, not to this final PR,
    because each step has already been reviewed.
  - The feature branch is deleted after the merge.
- **Keep the feature branch current.** When `main` changes, merge `main`
  into the feature branch through a PR. Never rebase or force-push a feature
  branch, because other branches start from it.
  - Exception: while the feature branch has no commits of its own (no step
    merged yet), move it to `main` with a fast-forward push
    (`git push origin origin/main:<feature-branch>`), with no PR. Nothing is
    rewritten, so open step PRs are not affected.
- **Link every PR in the backlog.** Right after `gh pr create`, push one
  commit to the same branch, `docs: link #N in backlog`. It adds `[#N]` to
  the item's PRs column in `docs/BACKLOG.md` and the definition
  `[#N]: <PR URL>` to the PR links block at the end of that file. This
  covers step PRs, follow-ups and the final feature → `main` PR. A change
  with no backlog item has no row to link.
- **An item with a single step needs no feature branch.** Its branch starts
  from `origin/main` and its PR targets `main`. The same applies to changes
  that are not backlog items, such as docs or process changes.
- **Every branch is worked on in its own worktree.** Create it from the
  repository root with
  `git worktree add .worktrees/<branch> -b <branch> origin/<base>`, where
  `<base>` is the feature branch for a step and `main` otherwise.
  `.worktrees/` is git-ignored.
- **After a merge, clean up with `scripts/after-merge.sh`.** For every
  worktree whose branch has a merged PR, it removes the worktree and deletes
  the local and the remote branch, then rebases the local `main` on `origin/main`. It skips
  a worktree with uncommitted changes or with commits that are not in the
  merged PR, and keeps a remote branch with such commits, and says why. Claude Code runs it through two hooks in
  `.claude/settings.json`: after any `gh pr merge`, and when a prompt
  mentions a merge or a PR number (`#N`). Run it by hand after merging on
  GitHub, or with `--dry-run` to see what it would do.
- **The PR description follows `.github/pull_request_template.md`.** It has
  these sections:
  - the title line: the backlog item and the step, if any;
  - the backlog path, the link to the spec and the base branch;
  - **What changed**: a summary, plus the changed line count;
  - **How to test**: steps the reviewer can follow to see the change working,
    with fictitious data only;
  - **Tests**: the test output;
  - **Verification**: the results of the spec's verification checks. Every
    box is checked. The only exception is a *Pending validation* check
    (the owner's real data), labeled as such. A check that waits on a later
    item means the spec is wrong: stop and fix the spec before opening the
    PR.
- **The product owner reviews and merges.** The author never merges their
  own PR.

## Note on Figma

The previous flow used Figma through its MCP server. It was suspended because
the Starter plan limits the number of MCP calls, which makes it impossible to
iterate on and verify the prototypes. The old file is still available for
reference at https://www.figma.com/design/sI5dvQYHtGMOwCUhgI7LrK. It is no
longer the source of truth for the design. Each screen is an independent
`.screen` element, so the HTML prototypes can be imported into Figma later if
that flow is resumed.
