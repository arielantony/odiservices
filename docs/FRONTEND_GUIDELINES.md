# Frontend Guidelines — OdiServices

How we create or extend a product's frontend, step by step. This guide puts
`docs/CONSTITUTION.md` (Articles 2 to 5) into practice. If the two ever
disagree, the constitution wins.

It applies to any person or AI agent working on the frontend.

## The process at a glance

| # | Step | Who | Output |
|---|---|---|---|
| 1 | Brief | Product owner | Short description, examples, acceptance criteria or guidelines |
| 2 | Clarifying questions | Agent | Up to 4 questions, or a list of assumptions |
| 3 | Prototype | Agent | `docs/prototypes/<feature>/vN.html`, verified in a browser |
| 4 | Review | Product owner and team | Feedback that leads to a new version, or approval |
| 5 | Stories | Agent | Gherkin `.feature` files in `docs/stories/` |
| 6 | Spec | Agent, approved by the product owner | One spec per story in `docs/specs/` |
| 7 | Implementation | Agent or developer | Code in `app/` that matches the approved version and spec |

Steps 3 and 4 repeat until the prototype is approved. Nothing in `app/`
changes before step 7.

## Step 1 — Brief

The product owner describes the feature in a few lines. The brief does not need
to be complete or formal. Three parts are enough:

- **Description:** what the feature is, who uses it and what it is for.
- **Examples:** concrete situations or data that show the feature in use,
  always with fictitious data.
- **Acceptance criteria or guidelines:** what must be true for it to be
  accepted, plus any constraint to follow, such as brand guidelines, an
  existing screen or a reference.

Template:

```markdown
**Feature:** <name>
**Description:** <who uses it, what it does, why>
**Examples:**
- <situation or sample data>
**Acceptance criteria / guidelines:**
- <criterion, constraint or reference>
```

## Step 2 — Clarifying questions

Before prototyping, the agent may ask **up to 4 questions**, in a single
message:

- Ask only what changes the prototype. Skip anything that has a sensible
  default, or that the code, the docs or earlier prototypes already answer.
- Give each question a recommended option, so a short reply ("ok", "1 and 3")
  is enough.
- Good topics: who the main user is, the primary task on the screen, which
  states matter (empty, error, loading, many items), and where the brief leaves
  room for more than one reasonable design.
- If the brief is clear, skip the questions and go to step 3. In that case,
  list the assumptions at the top of the presentation.
- For questions the owner doesn't answer, the recommended option becomes an
  assumption and is listed in the presentation.

## Step 3 — Prototype

The agent builds the prototype by following Article 3 of the constitution:

- one self-contained HTML file per version;
- one `.screen` per screen;
- the Odisseia brand;
- AA contrast;
- fictitious data only.

On top of those rules:

- **Start from what exists.** Reuse the tokens and patterns of the latest
  approved prototype. Only depart from them when the brief asks for it.
- **Interface copy in pt-BR**, as final as possible: specific button labels
  ("Enviar fatura", not "Enviar") and plain-language error messages. Stories
  and tests will quote these strings.
- **Design the states, not just the happy path.** For each screen, include the
  states that the brief or the questions marked as relevant, such as empty,
  loading, error and long content. List any state that was left out in the
  presentation.
- **Keep the history.** Store the versions in `docs/prototypes/<feature>/` and
  update its `README.md` with the version log (see below). If the HTML is
  generated by a script, keep the script and template next to it.
- **Verify before presenting** (Article 4). Open the file in a browser and
  check a full-page screenshot for overflowing text, overlapping elements,
  font fallback and colors outside the tokens.

## Step 4 — Review

The agent presents the version following Article 5:

1. the file path;
2. what changed;
3. how the brand was applied, and any deviations;
4. open questions;
5. the states that are not covered yet;
6. the assumptions from step 2, if any.

The product owner and the team review it:

- **Feedback** produces a new version (`vN+1`). The previous version is never
  overwritten.
- **Approval** is explicit, for example "v3 approved". The agent records it in
  the version log.
- Partial approval is allowed ("approved except the upload states"). The parts
  not approved go into the next version.

### Version log

Each `docs/prototypes/<feature>/README.md` keeps a table like this:

| Version | Date | Summary | Status |
|---|---|---|---|
| v3 | 2026-10-30 | Odisseia brand applied | In review |

Status values are *In review*, *Approved* and *Superseded*.

## Step 5 — Stories

After approval, the agent writes or updates the stories in `docs/stories/`,
following the conventions in `docs/stories/README.md`:

- one Gherkin `.feature` per story;
- scenarios that quote the approved copy exactly;
- tags that point to the approved prototype version.

Each story is then listed in `docs/BACKLOG.md` with its dependencies.

Stories can be drafted from a prototype that is still in review, to serve as a
review checklist. They stay **Draft** until approval.

## Step 6 — Spec

Before any code, the agent writes a spec for the story in `docs/specs/`,
following `docs/specs/README.md`:

- scope and out of scope;
- the reference measurements taken from the prototype in the browser;
- the behavior the prototype does not show;
- the changes per file;
- one verification check per scenario;
- open questions with a recommended option.

Before asking for approval, check the Verification section against the
Depends on line: every check runs with only this item and its dependencies,
when the item merges (`docs/specs/README.md`, section 4). Move any check that
needs a later item to that item's spec.

The product owner approves it explicitly ("spec FE-01 approved"). A story
becomes **Ready** when its prototype is approved, its scenarios have been
reviewed and its spec is approved. Backend tasks follow their own process
(`docs/BACKEND_GUIDELINES.md`). When a story needs an endpoint, the backend
spec defines the contract and the story's spec links to it.

## Step 7 — Implementation

- Implement only **Ready** stories, matching the approved version and spec.
- A story is **Done** when all of its scenarios pass, the page has been checked
  in the browser and the console shows no errors.
- If the design needs to change during implementation, go back to step 3 with a
  new prototype version. Don't change the design directly in the code.
- If the spec turns out to be wrong, update it and get it approved again before
  the code continues.
